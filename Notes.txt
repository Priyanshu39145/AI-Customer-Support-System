
🧠 AI-Powered Customer Support Backend — What I Have Built So Far

I started by designing the core structure of a real-world customer support system. First, I identified the main actors involved in the system: User, Agent, and Admin. Instead of creating separate tables for each, I used a single User entity with a role field (enum) to differentiate between them. This is a standard industry approach called role-based design, which keeps the system simple and scalable.

Next, I designed the core entities of the system: User, Ticket, and Message.

The User entity stores basic information like name, email, password, role, and timestamps. I ensured that the email is unique and important fields like name and password are non-null. I also used enums for roles (USER, AGENT, ADMIN) and stored them as strings in the database to avoid future issues.

The Ticket entity represents the main feature of the system. Each ticket contains a title, description, status (OPEN, IN_PROGRESS, RESOLVED), and priority (LOW, MEDIUM, HIGH). I added relationships to show that a ticket is created by a user and can be assigned to an agent. I also handled timestamps for tracking creation and updates. Additionally, I made sure that a ticket can exist without an assigned agent initially.


Then I designed the Message entity, which represents the conversation inside a ticket. Instead of building a direct messaging system (like WhatsApp), I followed a thread-based design, where each ticket acts as a conversation container. Messages belong to a specific ticket and are sent by a user (either the customer or the agent). This design is used in real support systems and allows features like conversation history and AI summarization.

I also implemented relationships between entities:
	•	A User can create multiple tickets
	•	A User (agent) can be assigned multiple tickets
	•	A Ticket can have multiple messages
	•	A Message belongs to one ticket and one sender

To make the system more complete, I added bi-directional relationships, meaning entities can reference each other in both directions. For example, a User can access their tickets, and a Ticket can access its messages.

However, this created a problem called infinite recursion when returning data through APIs. Because entities were linked in loops (User → Ticket → Message → User…), the system could crash or return huge nested JSON responses. To fix this, I used @JsonIgnore on certain fields to prevent unnecessary data from being serialized, ensuring clean and safe API responses.


I also made several important technical decisions:
	•	Used UUIDs for primary keys
	•	Used @CreationTimestamp and @UpdateTimestamp for automatic time tracking
	•	Used TEXT type for long descriptions
	•	Used @JoinColumn for clear database relationships
	•	Used Lombok to reduce boilerplate code

Overall, I have successfully built a solid backend domain model that reflects how real-world customer support systems work. The system now has proper structure, relationships, constraints, and is ready for the next phase, which includes repositories, service layer, and API development.

🧠 AI-Powered Customer Support Backend — Progress After Entity Design

After completing the entity design and database mapping, I moved to the backend implementation phase, where I started building the actual system behavior using repositories, service layers, and APIs.


🗄️ Repository Layer

I created repository interfaces for all core entities (User, Ticket, Message) using Spring Data JPA. These repositories extend JpaRepository, which provides built-in methods for common database operations like save, find, delete, and pagination.

For the Ticket entity, I added custom query methods to support filtering and pagination:
	•	Find tickets by status
	•	Find tickets by priority
	•	Find tickets by both status and priority

This allowed me to build flexible APIs without writing complex SQL queries.

⸻

⚙️ Service Layer (Business Logic)

I implemented a service layer to handle all business logic instead of putting logic inside controllers. This follows clean architecture principles and makes the code more maintainable and testable.

⸻

🎫 Create Ticket API

I built the first core API to create tickets.

Key logic implemented:
	•	Fetch user from database using userId
	•	Validate that the user exists
	•	Create a new ticket with:
	•	status = OPEN
	•	priority = user-provided or default (MEDIUM)
	•	assignedTo = null
	•	Save ticket to database

I used DTOs (Data Transfer Objects) to separate request and response from internal entities:
	•	CreateTicketRequestDTO for input
	•	CreateTicketResponseDTO for output

I also used ModelMapper to convert entity objects to DTOs and manually handled fields like IDs when needed.

⸻

📄 Get Tickets API (Pagination + Filtering)

Next, I implemented a scalable ticket retrieval API, which is a very important feature in real-world systems.

This API supports:
	•	Pagination using page and size
	•	Filtering by:
	•	status
	•	priority

I handled multiple cases in the service layer:
	•	Both status and priority present
	•	Only status
	•	Only priority
	•	No filters (return all tickets)

I used Spring’s Pageable and PageRequest to efficiently fetch paginated data from the database and mapped results to TicketResponseDTO.

This step helped me understand how to build APIs that can handle large datasets efficiently.

⸻

🧑‍💼 Assign Ticket API (Admin Feature)

I then implemented the feature where an admin assigns a ticket to an agent.

Key logic:
	•	Fetch ticket and agent from database
	•	Validate both exist
	•	Ensure the selected user has role = AGENT
	•	Assign the ticket to the agent
	•	Update ticket status from OPEN → IN_PROGRESS
	•	Return updated ticket as DTO

I also learned how to handle nested mapping issues when converting entities to DTOs. Since DTO should not expose full entities, I used fields like assignedToId instead of including the entire User object and manually mapped it.

This step introduced me to:
	•	Role validation
	•	Update operations
	•	Real-world business rules

⸻

🔄 Update Ticket Status API (Agent Feature)

Finally, I implemented the API to update ticket status, completing the ticket lifecycle.

Key logic:
	•	Fetch ticket from database
	•	Ensure the ticket is assigned to an agent
	•	Validate allowed status transitions:
	•	OPEN → IN_PROGRESS
	•	IN_PROGRESS → RESOLVED
	•	Prevent invalid transitions like:
	•	OPEN → RESOLVED
	•	RESOLVED → any other state
	•	Update status and return response

This introduced the concept of state machine validation, which is widely used in real systems to control workflow transitions.
