What SecurityConfig does? ----
SecurityConfig is the central file that controls the entire security system of your backend application. It tells Spring Security which endpoints are public, which require login, which roles can access specific APIs, how JWT authentication works, how OAuth2 login works, how CORS is handled for the frontend, how rate limiting is applied, and what should happen when authentication or authorization fails. In simple words, it acts like the “main security gatekeeper” of your whole backend.

In this project, when a user registers, the backend first checks if the email already exists. If not, it securely encrypts the password and saves the user in the database with the default USER role. During login, Spring Security verifies the email and password, and after successful authentication the backend generates two tokens: an access token (JWT) for accessing secured APIs and a refresh token for creating new access tokens later. The JWT token is sent in API requests and is validated by the JWTAuthFilter, which checks whether the token is valid, extracts the user information from it, and authenticates the user inside Spring Security. When the access token expires, the frontend sends the refresh token to /auth/refresh. The backend then checks whether the refresh token is valid, not expired, and not revoked. If valid, the old refresh token is revoked immediately and new access and refresh tokens are generated and returned to the frontend. This keeps the authentication system secure while allowing users to stay logged in without entering their password again and again.

The Conversation Flow is responsible for managing a user’s chat conversations. When a user opens the AI Chat page, the frontend calls the /conversations endpoint, which fetches all of that user’s non-deleted conversations from the database and returns them as simple DTOs for display in the sidebar. The user can search conversations using a keyword, where the backend searches both conversation titles and message contents while ensuring only that user’s conversations are searched. Users can also rename conversations, close conversations by marking their status as CLOSED, or delete them. Deletion supports both soft delete (marking the conversation as deleted and storing a deletion timestamp) and permanent delete (removing it from the database after safely breaking any linked ticket relationship). Before any sensitive operation like rename, close, or delete, the backend validates ownership to ensure that users can only access and modify their own conversations. Redis caching is used to speed up conversation retrieval, and the cache is automatically cleared whenever conversations are modified. Overall, the Conversation Flow provides secure conversation management, search, caching, ownership validation, and lifecycle control for all user chat histories.

Now we will go for the Ticket Management Flow ---- Go to the Ticket Controller ---- and accordingly navigate from there ----
The Ticket Management Flow is designed around a role-based support system where Users, Agents, and Admins interact with tickets through controlled workflows. A User can manually create a ticket by providing a title, description, and optionally a category, after which the system automatically assigns the ticket to the least-loaded agent with matching expertise (or the least-loaded available agent if no specialist exists), sets its initial status to OPEN, priority to MEDIUM by default, persists it, and records the action in the TicketActivity audit trail. Agents are responsible for handling assigned tickets and can progress them through a strict lifecycle of OPEN → IN_PROGRESS → CLOSED, ensuring invalid transitions are prevented, while also being able to modify ticket priority and category when necessary. Admins have elevated privileges allowing them to manually assign tickets to agents, change ticket metadata, and view all tickets across the system. Every meaningful change—ticket creation, assignment, status updates, priority changes, category modifications, and future comment additions—is logged as a TicketActivity entry containing the actor, action type, previous value, new value, and timestamp, providing a complete audit history. Users can view only their own tickets, agents can view tickets assigned to them, and admins can access all tickets, with authorization enforced through both Spring Security role checks and service-level validation. Ticket retrieval supports extensive filtering by keyword, status, priority, category, assigned agent, and creation date range, combined with pagination for scalability. To improve performance, frequently accessed data such as ticket details, ticket histories, and search results are cached using Spring Cache, while cache entries are automatically invalidated whenever a ticket is created or modified to maintain consistency. Detailed ticket views expose creator, assignee, conversation, status, priority, category, and timestamps, while history endpoints provide a chronological timeline of all ticket-related actions. The flow also integrates supporting services such as email notifications when tickets are resolved, agent load-balancing logic for assignment, transactional boundaries to guarantee data consistency, and repository-level search queries for efficient filtering. Overall, the architecture combines authorization, auditability, caching, searchability, automated assignment, and lifecycle management to provide a complete production-style customer support ticketing system.

Now we will go for the Agent Management Flow --- where the admin can get all the Agents --- and then assign their categories ----
The Agent Management Flow is responsible for managing support agents and their areas of expertise within the ticketing system. An Admin can assign one or more categories (such as Technical, Payment, General, etc.) to an agent using the /agents/{agentId}/categories endpoint, which validates that the target user exists and has the AGENT role before updating their expertise set. Whenever categories are changed, related ticket search caches are evicted to ensure future ticket assignments use the latest agent skills. The /agents endpoint allows Admins to fetch all available agents along with their basic information, expertise categories, and the number of currently active tickets (OPEN or IN_PROGRESS) assigned to them, enabling manual ticket assignment decisions and workload balancing. Initially, the implementation suffered from an N+1 Query Problem where one query fetched all agents and then an additional count query was executed for every individual agent to determine their active ticket count, causing database calls to grow linearly with the number of agents. This was optimized by introducing a single aggregation query (getAgentTicketCounts) that retrieves ticket counts for all agents at once, storing the results in a HashMap (agentId → activeTicketCount) and then constructing the response DTOs without issuing further database queries. As a result, the database workload was reduced from 1 + N queries to a constant 2 queries, making the agent listing endpoint significantly more scalable and production-ready while preserving the same API response structure.

Now seeing the uploading of the pdf Flow by the Admin ---- go to Company Policy Controller ---
When an Admin uploads a company policy PDF through the /admin/company-policy/upload endpoint, the controller first validates that the file is not empty, is actually a PDF (using both content-type and PDF magic-byte validation), and is within the allowed size limit. The file is then converted into a Spring Resource and passed to an asynchronous service method, which immediately returns a 202 Accepted response to the client while the actual ingestion continues in the background. Inside the service, a SHA-256 hash of the PDF is generated and checked against the database to prevent duplicate uploads, with an additional database-level unique constraint ensuring safety against concurrent requests. A version number is assigned based on previously uploaded policies with the same filename. The PDF is then passed to the DataLoader, which uses Spring AI’s PagePdfDocumentReader to extract text page by page into Document objects. These documents are sent to the DataTransformer, which uses a TokenTextSplitter to divide them into smaller overlapping chunks optimized for embedding and retrieval. Each chunk is enriched with metadata such as source filename, file hash, upload timestamp, chunk ID, and policy version. The enriched chunks are then embedded and stored in the vector database through the VectorStore, making them searchable during RAG retrieval. Finally, a CompanyPolicy record containing information like filename, hash, version, upload time, and processing status (PROCESSING, ACTIVE, or FAILED) is stored in the relational database, allowing future duplicate detection, version tracking, and monitoring of ingestion progress. During AI conversations, the vector store uses these stored chunks to retrieve the most relevant policy information, enabling the AI assistant to answer customer questions based on the company’s uploaded policies.

The AI chat flow starts when an authenticated user sends a message to the /api/chat endpoint. The ChatController receives the user’s message along with an optional conversation ID and forwards the request to the ChatService. The backend first validates the conversation. If a conversation ID is provided, it checks whether the conversation exists, belongs to the current user, is not deleted, and is not closed. If no valid conversation exists, a new conversation is automatically created. This ensures users can only access their own conversations and prevents interaction with invalid conversations.

Once the conversation is validated, the user’s message is immediately stored in the database. Storing messages before AI processing ensures that complete chat history is always available and can be used as context for future AI responses. The backend then fetches the recent conversation history and constructs a conversation context. To keep prompts efficient and reduce token usage, only the latest ten messages are included. Before this history is sent to any AI model, it is sanitized by removing or replacing suspicious phrases such as “ignore previous instructions”, “you are now”, and “system:”. Control characters are removed, excessive whitespace is normalized, and the history length is restricted to 3000 characters. This helps reduce prompt injection risks and prevents users from influencing the AI through previous messages.

After preparing the conversation history, the backend creates a comprehensive IntentContextDTO. This context contains information about the user, such as the number of tickets created today, the number of tickets created within the last hour, and the timestamp of the most recent ticket. It also contains session information such as the number of messages in the conversation, the conversation start time, and whether the current message is the first message. Finally, it includes conversation-specific information such as whether a support ticket already exists, the sanitized conversation history, and the current user message. This context allows the AI to make better decisions because it has information about both the user’s behavior and the current conversation.

A major improvement in the revised architecture is that security validation now occurs before intent analysis. Previously, the AI was called first and security checks happened later. Now, the SecurityValidationService examines the user’s message before any AI call is made. It looks for prompt injection attempts using patterns such as “ignore previous”, “jailbreak”, “act as”, “assistant:”, and “developer:”. It also detects abuse attempts such as ticket spamming and mass escalation requests. Additionally, it enforces ticket rate limits by restricting the number of tickets a user can create within an hour or a day and ensures a minimum cooldown period between ticket creation attempts. If any of these checks fail, the system immediately returns a safe error message without making any AI request. This reduces AI costs, improves security, and prevents malicious prompts from reaching the language model.

If security validation passes, the system performs intent analysis using the lightweight llama3.2:3b model. This model is not responsible for generating customer-facing responses. Instead, it performs intent classification and returns structured JSON indicating whether the user wants escalation, whether the user is requesting follow-up information about an existing ticket, a confidence score, and a short reason. To improve performance, the results of intent analysis are cached using a key based on the current message, ticket existence status, and conversation history hash. If the same context is analyzed again, the cached result is returned without making another AI call.

The backend never fully trusts AI output. After receiving the classification result, it parses and normalizes the response. If a ticket already exists for the conversation and the AI recommends escalation, the backend automatically converts the request into a follow-up request because only one ticket can exist per conversation. Similarly, if the AI recommends a follow-up request when no ticket exists, the backend removes that follow-up classification. Confidence values are clamped to a valid range, and missing fields are replaced with safe defaults. This ensures that business rules are always enforced by the backend rather than by the AI.

After normalization, deterministic backend routing rules are applied. These rules act as an override layer above the AI. For example, if the user explicitly requests ticket creation and also describes a genuine issue such as a payment failure, refund problem, account lockout, or application error, the backend can force escalation even if the AI is uncertain. This follows the principle that AI provides recommendations while the backend remains the final authority for business decisions.

Based on the final intent classification, the system chooses one of four execution paths. If the user is asking about an existing support ticket, the follow-up path is selected and ticket details are fetched through the getTicketDetails tool. If the user has a legitimate issue and escalation confidence is high, the ticket creation path is selected and the backend creates a support ticket. If escalation confidence is moderate, the system enters a clarification flow where the AI generates exactly one concise clarification question to gather more information. If neither escalation nor follow-up is required, the request is treated as a normal customer support conversation.

For normal conversations, the system uses the larger conversational model llama3.1. This model has access to a single tool called searchCompanyPolicy. The tool performs semantic similarity search against company policy documents stored in the vector database. Relevant documents are retrieved and provided to the model as reference material. The AI then generates a concise customer-facing response based on those documents. Results from policy searches are also cached to reduce vector database load and improve response times.

When a support ticket must be created, several additional backend validations are performed. The user message must be sufficiently descriptive, repetitive or spam-like text is rejected, and the message must contain meaningful content. The system also prevents duplicate ticket creation by ensuring that only one ticket can exist per conversation. Race conditions are handled through database constraints and exception handling. Once validation succeeds, the user’s message is sent to the AI ticket analysis service. Using the lightweight model, the system automatically generates a ticket title, category, priority level, and reasoning. These AI-generated values help standardize support tickets while reducing manual effort.

Whenever a backend tool returns structured data, the conversational model is used to convert that structured output into a natural and user-friendly response. Instead of showing raw JSON or map objects, the AI generates professional customer-facing messages. For example, after successful ticket creation, the user receives a confirmation message containing the ticket information in a readable format.

Another improvement in the revised version is fault tolerance. The normal conversational AI flow is wrapped in a try-catch block. If the AI model becomes unavailable or an unexpected error occurs, the system does not crash. Instead, it logs the error and returns a safe fallback message informing the user that the request cannot currently be processed. This improves reliability and prevents failures from affecting the user experience.

Finally, every AI-generated response is stored in the database just like user messages. This ensures complete conversation history, enables auditing, and provides future context for subsequent AI interactions. The backend then returns an AIResponse object containing the original user message, the generated AI response, the conversation ID, and a timestamp. The overall architecture follows a clear separation of responsibilities where AI is responsible for understanding language, classifying intent, generating ticket metadata, asking clarification questions, and producing natural language responses, while the backend remains responsible for security, validation, authorization, business rules, routing decisions, ticket management, and system reliability. This makes the system significantly more secure, predictable, maintainable, and closer to the way production AI-powered customer support platforms are built in real companies.
